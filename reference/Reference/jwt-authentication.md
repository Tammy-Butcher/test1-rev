Vbrick Rev supports authentication based on signed and encrypted **JSON Web Token (JWT)** also known as **JSON Web Encryption (JWE)**. 

**JWE** is a standard to securely exchange data between two trusted parties in JSON format. Here the trusted parties are Vbrick Rev and Customer/3rd party applications. Customer or 3rd party application/software henceforth will be called 3rd party applications in this topic.

## Process Overview

The first step in the process is to obtain a signed JWT. To start this process, Vbrick uses a customer generated **X.509 public/private key pair (signing key)**. 

- The 3rd party application holds the **private key** and Rev has the **public cert** of this signing key. 
- The 3rd party application will sign the JSON (see below for the details of the JSON structure) with the **private signing key** which then generates signed JWT tokens. This signing process ensures the token has not been tampered with. 
- This signed JSON is called the **Signed JWT**.

To start this process, access **System Settings** > **User Security** > **JWT Authentication** section and click the **Enable JWT Authentication & Authorization** checkbox.

Click the **Add New** button to upload your signing certificate and then generate and download your new encryption certificate.

For additional security, along with signing the JWT, Vbrick also encrypts the signed JWT to create a **JWE token**. 

- The encryption uses a second public/private key pair that will be generated by Rev (called an **Encryption Key**), where the 3rd party application will hold the **public key** and Vbrick Rev will have the **private key** of the **Encryption Key**. 
- The 3rd party application will encrypt the signed **JWT token** with the **public Encryption key** to generate the **JWE token**. 
- This final JWE token that is what will be used to authenticate a user against Vbrick Rev.

## Examples

Vbrick Rev supports two types of JWTs for providing access:

**SSO (Read/Write)**: The standard JWT is used as an alternative to the Rev Single Sign-On process. It provides the same level of access as if a user logs in via OAuth or through the Rev Portal. The user specified as the Subject ("sub") _must_ exist in Rev.

**Trusted Public (Read Only)**: This JWT is used to grant **Media Viewer** level access to a _single_ resource (Video/Webcast). Resources _must_ explicitly have "**External Application**" access enabled. This allows for viewing of resources without a login required. Note that if the email address of an existing Rev User is specified then that use must _not_ be suspended and otherwise have access to the resource.

> 🚧 Important!
> 
> **Trusted Public (Read Only)** JWT access has **limited write operations** such as adding video comments or asking a question in a webcast event if allowed (enabled).

### Signed JWT

Signed JWT is also known as JSON Web Signature (JWS). The JWT token generated by 3rd party application will consist of the three parts (header, payload, signature).

**Header:** The header consists of these elements:

- alg – This is the signing algorithm being used, “**RS256**” (**RSA 256**) in our case. 
- type – This will be “**jwt**” 
- kid (optional) – **key id** used for signing the JWT. Its value should be base64url-encoded SHA-1 thumbprint (a.k.a. digest) of the signing key/certificate.

```json Example
{ “alg”: “RS256”, “type”: “jwt”, "kid": "NUYgQTcgQ0YgMTAgMzAgMjUgQzcgOUUgOEEgNDggMUMgMzAgMzEgODQgN0MgMTAgNzYgN0UgN0MgQzM"}
```

**Payload:** This part consists of the claims for the user. It consists of some standard JWT claims and other custom claims to identify the user.

**Standard:**

**Signature:** To create the signature part, the 3rd party application will base64 encode the **Header** part, base64 encoded the **Payload** part, and append these two parts separated by a dot and sign this appended string using the **private key** of the **signing key** and algorithm (**RSA 256**) to create the signature.

- SIGN(base64UrlEncode(Header) + "." + base64UrlEncode(Payload)) using private key and RSA 256 algorithm

**Final JWT:** The final JWT will be a token with three parts separated by dot.

- bas64encodedHeader.base64encodedPayload.signature  

### Encrypted JWT (JWE)

The 3rd party application will take the **signed JWT** and encrypt it using content encryption **A256GCM** and key wrapping algorithm **RSA-OAEP-256**.  The **JWE token** consists of five parts (JOSE header, JWE encrypted key, JWE initialization vector, JWE ciphertext, JWE authentication tag, and final JWE).

**JOSE Header:** The JOSE header consists of the following header elements.

- enc - defines the content encryption algorithm. Its value should be "**A256GCM**". 
- alg - defines the encryption algorithm for the Content Encryption Key (CEK). Its value should be "**RSA-OAEP-256**"
- kid (optional) - cert id used for encryption. Its value should be **base64url-encoded SHA-1 thumbprint** (a.k.a. digest) of the Vbrick Rev's encryption key/certificate.

```json Example
{"enc":"A256GCM","alg":"RSA-OAEP-256", "kid": "AgMjUgQzcgOUUgOEEgNDggMUMgNUYgQTcgQ0YgMTAgMzMzAgMzEgODQgN0MgMTAgNzYgN0UgN0MgQzM"}
```

**JWE Encrypted Key:** During the encryption process, the 3rd party application generates a symmetric random key (i.e. **Content Encryption Key (CEK)**), which is 256-bits in size, that is used to encrypt the **JWT payload**. This CEK itself is encrypted using the Vbrick Rev's public key and algorithm defined in the **alg (RSA-OAEP-256)** element of the JOSE header. The encrypted key is placed in the **JWE Encrypted key** section.

**JWE Initialization Vector:** Some encryption algorithms require an initialization vector, which is a randomly generated number that is used along with a secret key to encrypt data. This prevents repeated encryption of the same data using the same secret key. This initialization vector is also used to decrypt the message, and hence, is placed in the JWE token.

**JWE Ciphertext:**  Encrypt the **signed JWT JSON payload** (from the **JWT section**) using the CEK, the JWE Initialization Vector, and the Additional Authenticated Data (AAD), using content encryption method **A256GCM**. This produces ciphertext and the **Authentication Tag**. The fourth section of the token is the ciphertext generated. 

**JWE Authentication Tag:** The authentication tag is the last part of the JWE Token generated along with the ciphertext. It ensures the integrity of the ciphertext.

**Final JWE:** The final JWE will be a token with 5 parts separated by dot.

- bas64URLencode(UTF8(JOSE Header)) + "." + bas64URLencode(JWE Encrypted Key) + "." + bas64URLencode(JWE Initialization Vector) + "." + bas64URLencode(JWE Ciphertext) + "." + bas64URLencode(JWE Authentication Tag)
